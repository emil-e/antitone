# Match retained storage to source precision

Uncorrected development is RGB16. Retaining its four native u16 slots preserves that integer information compactly. Sony lens development instead produces fractional camera samples and shading can exceed the native RGB16 range: those originals retain three-channel f32 and release the redundant native RGB16 image. Original CFA remains separate capture authority in both cases.

Storage precision and arithmetic precision solve different problems. Near film base, nonlinear inversion makes small rounding differences significant. Shader temporaries and small constants therefore use additional precision where needed without requiring wide arithmetic storage for every retained original. Bounded camera proxies and GPU uploads use code-unit f32, which represents all native u16 values exactly and does not requantize reconstructed samples.

Retained source format does not select inversion precision. Integer and continuous inputs use direct compensated inversion. Exact-code response caching was removed because the representative lens/flat-field-corrected workflow needs continuous processing; its integer-only acceleration did not justify separate runtime machinery. The positive editor prototype separately retains physical-view filtered signed/HDR AP1, not another float copy of the whole original. Its latency benefit depends on explicit upstream invalidation and immutable replacement lifetimes; complete concurrent native-memory admission remains acceptance work. Preview AP1 is deliberately approximate and never becomes original/export authority.

The architectural precedent is visible demand and upstream reuse, not cheap exact-export processing: [darktable 5.6.2](https://github.com/darktable-org/darktable/blob/release-5.6.2/src/develop/develop.c) requests visible ROI/display density, hashes preceding processing and can retain an old backbuffer while replacements run; [RawTherapee's coordinator](https://github.com/RawTherapee/RawTherapee/blob/b2ee504c47e5e6d5e054395aa12bf1fe43bd1c3c/rtengine/improccoordinator.cc) separates reduced preview/detail/export work. Their quality modes and algorithms differ. Neither establishes our preview/export correspondence or justifies lower precision, universal low-detail fallback or a cache after every stage.

A bounded [storage study](../diagnostics.md#sony-source-storage-precision) compares retaining fractional values with rounding to RGB16 within the native range. Plain RGB16 additionally loses post-shading headroom unless its scale/range representation changes. Most tested image differences were small, but a dense reference produced rare differences approaching two encoded 8-bit levels. In that study, integer-valued inputs substantially accelerated uncorrected inversion through the then-retained exact-code cache; that benefit disappeared with flat-field gains. Those timings are historical, not measurements of today's direct processing. Current f32 storage avoids another quantization and custom packing. It is a quality/complexity choice, not a demonstrated universal photographic necessity.

The current GPU implementation rejects unsupported numerical domains instead of falling back to CPU interactive processing. Rendered-only images need not retain unused source resources. [Sony development](../processing.md#embedded-sony-lens-correction) owns reconstruction/range rationale; [GPU processing](../../src/gpu.rs), [response tests](../../tests/gpu_film_response.rs) and [editor previews](../editor.md#fast-feedback-is-not-authoritative-data) own processing and lifetimes.
