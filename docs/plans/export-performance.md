# Export performance follow-up

Production export uses authoritative original-sample GPU processing, exact f64 reconstruction and CPU encoders. Straightened compositions now reuse completed tiles within one immutable job; the [output guide](../colour-and-output.md#tiff-and-exr-serve-different-purposes) owns that contract. Matched scalar/OCIO-reference measurements and bounded cache comparisons are available through the [full-size diagnostic](../diagnostics.md#export).

Bounded reuse, exact clipping/locality, range-reduced compensated GPU math and overlapped TIFF geometry planning reduce the measured latency, but do not establish isolated hardware throughput, a minimum chip/RAM target or universal latency. The reference adapter remains an independent measurement oracle, not a second production renderer or a reconstruction of an old binary.

## Remaining scope and acceptance

- Establish realistic latency/throughput expectations using matched hardware, source resolution, cold versus already-developed inputs, output format/compression, correction and straightening. Compare single-image latency separately from batch throughput; document prior-art measurement conditions rather than inventing a Lightroom baseline. Broaden characterization across source sizes, crop alignment, exact turns, both targets and output precisions. Include ordered locals and signed/HDR/floor/bypass cases in correctness checks and use a coordinated timing window before attributing small differences.
- Investigate output-specific representation separately from photographic arithmetic. Lossless f32 storage of already-rendered TIFF cache values demonstrated smaller tile payload, but no latency win on the measured traversal; it is not a selected performance default. Keep compensated AP1 for EXR and existing numerical gates. Any lower-precision arithmetic or future 8-bit path needs explicit final-output error bounds across the supported domain, not an assumption that final quantization makes earlier errors harmless.
- Use the stage breakdown before selecting further algorithms or scheduling. After overlapping CPU geometry with the single GPU consumer, further CPU planning micro-optimization may not reduce the critical path. The earlier two-slot GPU/batched-submit probes and small TIFF strip/buffer changes did not establish a useful gain; they are different from CPU-plan overlap.
- Evaluate lossless TIFF storage independently of processing: fast Deflate reduced measured encoding time and file size, while uncompressed output traded larger files for lower encoding cost. Both preserved tested RGB16/profile data, but neither is a selected default. Broader source/reader compatibility and an explicit format-policy decision are required before replacing LZW.
- More retained tile payload can reduce repeated GPU work, but capacity and traversal interact; choose any larger budget explicitly from measured benefit and memory/lifetime cost, not by silently increasing normal limits.
- Keep additional ownership explicit: completed geometry plans, construction/stack transients, completed CPU tile payload, current upload/readback, encoded frame, retained working detail/underlay and encoded/in-flight/native-retired resources. A bounded job cache is not a full-source float store or an aggregate admission guarantee. Measure benefit and lifetime before expanding it.
- Preserve existing original-processing, exact geometry, supplied-sample encoding, profile/metadata, immutable snapshot and destination-safety gates. Keep compensated AP1 through EXR reconstruction; no preview authority, early rounding, new clamp, unsupported-domain shrinkage or silent fallback.
- Repeat bounded resource observations with unchanged pressure, swap-counter, growth, duration and unavailable/stale-telemetry stops. Footprint, resident memory and Metal allocation overlap and must not be added. Do not improve a result by increasing normal cache limits or relaxing diagnostic allowances.

The [development checks](../development.md#export-checks) provide the normal verification route. Software agreement is not photographic or physical-display acceptance. Forced-pressure exercises, native application automation and system setup still require separate authorization. This plan records follow-up scope, not authorization to start it.
